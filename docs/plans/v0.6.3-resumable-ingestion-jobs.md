# v0.6.3 Resumable Ingestion Jobs Plan

## Goal

Make large repository ingestion recoverable when the browser disconnects,
the screen locks, the machine sleeps, or the frontend proxy connection drops.

## Problem

`POST /repositories/ingest` is currently a single blocking request. The backend
can keep working, but the browser has no durable job identity to reconnect to
after a tab reload, network reset, or OS session interruption. Large remote
repositories such as Polars can run long enough for that interaction model to
feel fragile even when the API and vector store remain healthy.

## Scope

- Add persisted ingestion jobs with stable `job_id`, repository address,
  lifecycle status, timestamps, summary, and error fields.
- Change the UI to start ingestion quickly and then poll job status.
- Keep the existing blocking endpoint for backward compatibility, or provide a
  clearly versioned compatibility path.
- Record enough progress metadata to show honest states without fake stage
  percentages.
- Preserve local-only Docker Compose and BYOK constraints.

## Proposed API

- `POST /repositories/ingest-jobs`
  - Creates an ingestion job and returns immediately with `job_id`.
  - Starts work in a background thread or task owned by the API process.
- `GET /repositories/ingest-jobs/{job_id}`
  - Returns `pending`, `running`, `completed`, `failed`, or `cancelled`.
  - Includes elapsed time, repository identity when known, final ingest summary,
    and a user-safe error detail.
- `POST /repositories/ingest-jobs/{job_id}/cancel`
  - Best-effort cancellation if the job has not reached an irreversible vector
    replacement step.

## Implementation Notes

- Prefer PostgreSQL persistence because monitoring and evaluation already depend
  on it in the local stack.
- Use in-process job storage only as the no-DSN fallback. Browser reload
  recovery across API restarts requires PostgreSQL.
- Keep Qdrant replacement semantics idempotent by commit hash.
- Do not add a new queue service for this release.
- Avoid token-level or fake stage streaming. Coarse states are enough:
  `queued`, `discovering`, `indexing`, `completed`, `failed`.
- If the API process restarts, jobs that were `running` should become `failed`
  or `interrupted` with a clear retry path.

## UI Behavior

- The ingest button starts a job and immediately shows the compact progress row.
- The row survives reload by reading the latest active job from storage.
- Details show job status, elapsed time, and last known backend state.
- Completion replaces progress with the normal repository receipt.
- Failure shows a retryable error with the backend-provided detail.

## Acceptance Checks

- [x] Starting ingestion returns a `job_id` without waiting for indexing to finish.
- [x] A browser reload during ingestion can recover the same job status.
- [x] A client disconnect does not cancel backend ingestion by default.
- [x] Completed jobs expose the same `IngestSummary` shape used today.
- [x] Failed jobs expose stable, user-safe error details.
- [x] Existing `/repositories/ingest` behavior remains compatible for CLI or older
  frontend builds.
- [x] Tests cover job creation, polling, completion, failure, interrupted jobs,
  duplicate same-revision ingestion, and frontend reload recovery.

## Out of Scope

- Distributed workers or external queues.
- Multi-user job ownership.
- Cloud deployment.
- Fine-grained progress percentages.
- v0.7 adaptive research streaming.
