# v0.6.2 Provenance and Feedback Hardening Plan

## Goal

Make release-to-release answer comparisons trustworthy before v0.7 adaptive
research changes routing behavior, and fix the current feedback frontend
behavior so monitoring data is not polluted by duplicate or ambiguous feedback.

## Scope

This is a hardening release, not a new research capability. It should ship
before v0.7 and keep `/rag`, `/research`, monitored-run evaluation, and the
evaluation dashboard backward compatible.

## Feature 1: Version-aware monitoring and evaluation comparisons

### Problem

- `pyproject.toml` and OpenAPI expose the current package version, but persisted
  monitoring and evaluation rows do not record the application version or source
  commit that produced each row.
- Post-hoc monitored-run evaluation can judge old answer snapshots using a newer
  judge/runtime. Without explicit versions, the dashboard cannot distinguish
  "old answer judged now" from "new answer judged now."
- Older rows can be inferred approximately from timestamps and release history,
  but should not be presented as exact unless the row was created after version
  capture was implemented.

### Data model

Add exact version metadata to new rows:

- `monitoring_runs.answer_app_version`
- `monitoring_runs.answer_git_commit`
- `monitoring_runs.answer_version_provenance`
- `answer_snapshots.answer_app_version`
- `answer_snapshots.answer_git_commit`
- `answer_snapshots.answer_version_provenance`
- `evaluation_runs.evaluation_app_version`
- `evaluation_runs.evaluation_git_commit`
- `evaluation_runs.evaluation_version_provenance`

Provenance values:

- `exact`: captured at write time from the running application.
- `inferred`: backfilled from timestamp windows and release history.
- `unknown`: not captured and not defensibly inferable.

### Implementation steps

- [x] Add a small version metadata helper that reads the installed
  `repo-deep-research` package version and the current git commit when
  available. If git metadata is unavailable inside a container or wheel, store
  `unknown` rather than failing the run.
- [x] Extend PostgreSQL schema initialization additively for existing local
  databases.
- [x] Extend typed models and API response models with nullable version fields.
- [x] Populate answer version metadata when recording direct and agentic
  monitoring runs and answer snapshots.
- [x] Populate evaluation version metadata when creating `evaluation_runs`,
  including post-hoc monitored-run evaluation.
- [x] Add a conservative backfill command or migration helper for legacy rows:
  infer from release timestamp windows only when a row falls cleanly between
  known release boundaries; otherwise keep `unknown`.
- [x] Expose answer and evaluation version fields in `/monitoring` and
  `/evaluations`.
- [ ] Add dashboard grouping/filter affordances for answer version and
  evaluation version where they help compare releases without cluttering the
  primary dashboard.

### Acceptance checks

- New direct and agentic runs persist exact answer version and git commit.
- New post-hoc evaluation runs persist exact evaluation version and git commit.
- The UI can compare answer quality by `answer_app_version` while showing which
  `evaluation_app_version` produced the judgment.
- Inferred legacy rows are visibly labeled as inferred or unknown.
- Tests cover schema initialization, persistence, API serialization, dashboard
  grouping, and conservative backfill behavior.

### Out of scope

- Re-judging all historical rows automatically.
- Treating inferred legacy versions as exact release evidence.
- Adding a new analytics database.

## Feature 2: Feedback frontend behavior hardening

### Problem

- Feedback controls remain active after a submission.
- The UI can submit duplicate feedback for the same answer/session.
- The current behavior does not make it clear whether feedback was accepted,
  already recorded, failed, or can be changed.

### Product behavior

- Feedback is a per-answer interaction keyed by `request_id` when available,
  falling back to `session_id` only for legacy rows.
- After successful submission, the answer view shows the recorded state and no
  longer invites accidental duplicate submission.
- Repeated clicks and network retries are idempotent.
- Changing feedback is either explicitly supported as a replace action or
  explicitly rejected with an already-submitted response. Do not silently create
  multiple rows for the same answer.

### Implementation steps

- [x] Add backend idempotency for feedback writes keyed by `request_id` when
  available and by `(session_id, run_kind)` only for legacy rows without
  request IDs.
- [x] Decide whether feedback replacement is allowed. If yes, use an explicit
  update/replace path; if no, return a stable already-submitted response.
- [x] Update API response models so the frontend can render current feedback
  state after a run and after a submission.
- [x] Disable or replace useful/not-useful controls after a successful
  submission.
- [x] Show recorded state: useful, not useful, or submitted with comment.
- [x] Re-enable controls only after a failed submission and show a useful error.
- [ ] Reflect submitted feedback immediately in the answer view and monitoring
  detail without requiring a page refresh.

### Acceptance checks

- One answer cannot receive duplicate feedback from repeated clicks.
- Refreshing the page preserves and displays the recorded feedback state.
- Failed submissions re-enable controls and show a useful error.
- Tests cover direct answers, agentic answers, legacy session-only rows, and
  repeated submission attempts.

### Out of scope

- Multi-user identity or authentication.
- Free-form feedback moderation.

## Verification

- Backend: focused recording-store/API tests for version metadata, backfill,
  and feedback idempotency.
- Frontend: focused feedback component/route tests for submitted, duplicate,
  failed, and legacy states.
- Contract: run `make export-openapi` after API model changes.
- Broad gate before release: `make test-all`.

## Release gate

- Package metadata, lockfile, README, OpenAPI, and release notes all say
  `0.6.2`.
- New monitoring/evaluation rows carry exact version provenance.
- Legacy rows are either inferred or unknown, never falsely exact.
- Feedback cannot be duplicated accidentally from the browser.
- v0.7 plan remains unchanged except for depending on this hardening release.
