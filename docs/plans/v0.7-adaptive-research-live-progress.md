# v0.7 Adaptive Research and Live Progress Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Select the cheapest adequate research path with an auditable deterministic policy and show safe lifecycle progress throughout long-running research.

**Architecture:** A new adaptive orchestration service wraps the existing direct and bounded-agentic services without changing evaluation behavior. It routes Quick, Balanced, and Thorough requests, performs at most one direct-to-agentic escalation, publishes typed lifecycle events through an injected progress reporter, and exposes both synchronous JSON and POST-based SSE endpoints.

**Tech Stack:** Python 3.12, FastAPI `StreamingResponse`, Pydantic v2, PydanticAI, React 19, TypeScript, Fetch `ReadableStream`, TanStack Query, pytest, Vitest

**Spec:** `docs/PRD.md` section 23; depends on the accepted v0.6.1 relationship-aware implementation, the v0.6.2 provenance/feedback hardening plan, and `docs/plans/v0.6.0-relationship-aware-change-impact.md`

## Global Constraints

- Complete the v0.6.1 graph-expansion acceptance gate before starting v0.7.
- Complete v0.6.2 provenance and feedback hardening before collecting v0.7
  comparison evidence.
- Keep routing deterministic and auditable; do not add an LLM router.
- Keep `/rag`, `/research`, CLI `ask`, CLI `research`, and evaluation direct/agentic modes backward compatible.
- Quick always uses direct RAG; Thorough always uses bounded agentic research with v0.6.1 graph expansion.
- Balanced uses inferred question mode plus explicit post-direct sufficiency rules and may escalate at most once.
- Record selection reason, attempted paths, escalation, total latency, and total model usage in the final trace.
- Emit application lifecycle events only; never expose hidden reasoning or raw chain-of-thought.
- Use POST plus Fetch streaming for SSE; do not put questions or repository paths into a GET query string.
- Stream lifecycle events and a validated final result, not partial answer tokens.
- Record exactly one completed user-visible adaptive run and answer snapshot, even after escalation.
- A disconnected stream may stop delivery but must not intentionally cancel persistence of a run already executing.
- Add no production dependency.

- [ ] **Step 4: Implement typed lifecycle events and reporter**

Use this event vocabulary exactly:

```python
class ProgressEventType(StrEnum):
    RESEARCH_STARTED = "research_started"
    RETRIEVAL_COMPLETED = "retrieval_completed"
    GRAPH_EXPANSION_COMPLETED = "graph_expansion_completed"
    FILE_INSPECTION_COMPLETED = "file_inspection_completed"
    ANSWER_GENERATION_STARTED = "answer_generation_started"
    RESEARCH_COMPLETED = "research_completed"
    RESEARCH_FAILED = "research_failed"
```

`ProgressReporter.emit()` assigns monotonically increasing sequence numbers under a `threading.Lock`, attaches one outer request ID and UTC timestamp, releases the lock, and then invokes a supplied `Callable[[ResearchProgressEvent], None]`. Event properties use `dict[str, str | int | float | bool]`. The no-op reporter has the same method and does nothing.

`ResearchStreamEnvelope` contains one `ResearchProgressEvent` plus exactly one of: a terminal `AdaptiveResearchResult`, a safe `StreamFailure`, or neither for intermediate events. This keeps progress properties scalar while allowing the terminal SSE frame to carry the complete validated result.
