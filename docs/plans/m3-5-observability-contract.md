# M3.5 - Observability Contract

## Goal

Add an application-owned trace contract around the existing direct-RAG response
so frontend testing, future feedback storage, Logfire instrumentation, and price
logging all share the same stable metadata shape.

M3.5 does not change answer generation behavior. It makes each direct-RAG run
auditable by separating answer content from runtime telemetry.

## Scope

- response envelope for direct-RAG runs;
- typed trace metadata generated by application code;
- latency, retrieval, repository identity, error, model usage, and estimated
  price fields;
- CLI and API contract updates that preserve the existing `RagAnswer` shape as
  the answer payload;
- focused tests for trace construction, price calculation, and response shape;
- documentation updates for consumers of the API and CLI JSON output.

## Non-goals

M3.5 must not add:

- React frontend work;
- feedback persistence;
- Logfire instrumentation;
- dashboards;
- database schema for telemetry;
- account-level spend tracking;
- aggregation, rollups, currency conversion, or billing reports;
- new model providers;
- agentic tool loops.

## Proposed response shape

Keep model-authored answer content separate from application-owned metadata:

```text
RagRunResult
- answer: RagAnswer
- trace: RagRunTrace
```

`RagAnswer` remains the grounded answer contract with summary, evidence,
implementation flow, change targets, risks, confidence, and unresolved questions.

`RagRunTrace` is generated by the service layer and is safe to log or persist
later.

## Trace fields

The first trace model should include:

```text
request_id
started_at
completed_at
repository_id
repository_name
branch
commit_hash
question_mode
retrieval_mode
retrieval_limit
retrieved_chunk_count
unique_file_count
evidence_ids
latency_ms_total
latency_ms_retrieval
latency_ms_model
model_usage
total_estimated_cost_usd
insufficient_evidence
error_type
error_message
tool_call_count
```

For direct RAG, `tool_call_count` is always `0`. M4 agentic research should
reuse the same field rather than inventing a parallel metric.

## Model usage and price logging

Represent model usage as reusable application telemetry:

```text
ModelUsage
- provider
- model
- input_tokens
- output_tokens
- total_tokens
- cached_input_tokens
- reasoning_tokens
- estimated_cost_usd
- pricing_source
- pricing_version
```

Rules:

- extract token usage from provider responses when available;
- estimate cost only for known configured models;
- use the default pricing table only when no override is supplied, so explicit
  empty pricing tables can disable estimates in tests or controlled runs;
- return `estimated_cost_usd = null` when pricing is unknown;
- treat pricing and usage enrichment as telemetry-only; malformed or
  inconsistent usage metadata must not suppress an otherwise valid answer;
- version the local pricing table so later reports can explain historical
  estimates;
- never ask the LLM to calculate or emit price fields.

## Implementation order

1. Add typed `RagRunResult`, `RagRunTrace`, and `ModelUsage` models.
2. Add a small pricing module for known configured model prices.
3. Capture provider usage in the OpenAI adapter without changing answer content.
4. Measure retrieval, model, and total latency in the service layer.
5. Return the response envelope from CLI and API.
6. Update contract tests and CLI tests.
7. Update usage documentation with the new JSON shape.

## Acceptance criteria

M3.5 is complete when:

- `/rag` returns answer content plus trace metadata;
- CLI JSON output returns the same top-level contract;
- direct-RAG answers still validate citations exactly as in M3;
- trace metadata includes repository identity, retrieval settings, latency,
  model usage, estimated cost where known, and tool-call count;
- unknown pricing is explicit rather than guessed;
- default tests do not require paid model calls.

## Status

Implemented as the direct-RAG answer-plus-trace reporting contract.
